- feat(api): Run untrusted input in a locked-down child process
  (`@cedarjs/api/sandbox`) (#3018) by @Tobbe

`@cedarjs/api/sandbox` runs a Node script on untrusted bytes, like an uploaded
photo or a third party's PDF, in a sandboxed child process. If a crafted file
exploits a bug in the parser (libvips, pdf.js, …), it lands in a process with an
empty environment (on Windows, a few system variables remain) that can read
only its own script, the packages you name (with their dependencies) and the
paths you allow, can't
write files, start processes or `eval`, and has no network. The child gets the
input on stdin and returns its result on stdout, with a heap cap, a timeout and
input and output limits.

```ts
import {
  createConcurrencyLimiter,
  findChildScript,
  runSandboxedChild,
} from '@cedarjs/api/sandbox'

const limit = createConcurrencyLimiter(2)

const result = await limit(() =>
  runSandboxedChild({
    script: findChildScript(import.meta.dirname, 'thumbnail.child'),
    packages: ['sharp'],
    allowAddons: true,
    input: bytes,
  }),
)
```

On Node 25+ Node's permission model blocks the child's network; on Node 24 a
preload takes it away from JavaScript. `findChildScript` finds the child script
in every build: `cedar build --ud` emits each `*.child.ts` to
`api/dist/ud/sandbox-children` with the packages it imports, `cedar setup deploy
netlify --ud` adds that folder to `included_files` in `netlify.toml`, and on
Vercel the build copies it into each function.

It builds on Node's permission model and is defense in depth, not a security
boundary: native addons (`allowAddons`, e.g. sharp) aren't limited by the
permission model. See `packages/api/src/sandbox/README.md`.
