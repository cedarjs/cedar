- feat(testing): guard cedar test's db reset by identity, add opt-in
  auto-consent (#2713) by @Tobbe

`cedar test api` resets your test database before each run. Cedar checks that
the resolved database is actually a dedicated test database, distinct from
`DATABASE_URL` — not just that its _provider_ matches `schema.prisma`.

Cedar refuses to run the reset when:

- the resolved test database is the same database as `DATABASE_URL` (same host,
  port, and database name, or the same sqlite file), or
- the database name doesn't look like a test database (it doesn't contain `test`
  or `e2e`).

Cedar's own generated sqlite fallback (`.cedar/test.db`, used when
`TEST_DATABASE_URL` isn't set) is exempt from the naming check, since it's a
path only Cedar controls — but it's still checked against `DATABASE_URL`. If
your team names test databases some other way, list the name in `cedar.toml`:

```toml title="cedar.toml"
[test]
  acceptedTestDatabaseNames = ["my_app_ci"]
```

or set `TEST_DATABASE_ACCEPT_TARGET=my_app_ci` for a one-off or CI-only
override.

Separately, Prisma refuses to run a destructive command like this when it
detects an AI agent, unless `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION` is
set. Since `cedar test api` runs such a command as part of its own test-database
setup, that guard can fire on Cedar's own invocation. An opt-in `cedar.toml`
setting handles this:

```toml title="cedar.toml"
[test]
  autoConsentToDbReset = true
```

With it on, Cedar supplies that env var for you automatically — but only once
the identity guard above has confirmed the reset target is a dedicated test
database. It's off by default, and never overwrites a consent value you've
already set yourself.

See the
[Testing docs](https://cedarjs.com/docs/testing#test-database-identity-guard)
and
[`cedar.toml` docs](https://cedarjs.com/docs/app-configuration-cedar-toml#test)
for details.
