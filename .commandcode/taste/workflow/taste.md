# Workflow

- After making code changes, verify by running: prettier, eslint, unit tests, and tsc on changed files before considering the change complete. Confidence: 0.80
- Add tests one at a time, verifying each passes before adding the next test. Confidence: 0.70
- Maintain backwards compatibility in semver minor releases; no mandatory breaking changes. Confidence: 0.75
- When uncertain whether a command/pattern works across package managers or platforms, test it empirically on the user's machine rather than deferring to existing patterns or speculating about edge cases. "Is this PM-agnostic?" is a question to answer by running the command, not by trusting prior assumptions. Confidence: 0.75
- Users never regenerate Cedar apps from templates. CedarJS guides them through manual updates and provides codemods to help them upgrade. Don't assume changes to template files will reach existing apps. Assume instead that they need migration paths. Confidence: 0.85
- Don't give up on a debugging task after a few failed attempts. The user expects continued investigation and tries the next viable angle (different config option, plugin API, build artifact inspection, runtime logging) rather than declaring the bug a known-issue and skipping tests. Persist through a "this needs a separate PR" decision unless the user explicitly agrees to punt. Confidence: 0.85
- Do not run `git commit` or `git push` unprompted — by default the user handles version control themselves. But when the user explicitly asks to create a branch and open a GitHub PR, that request authorizes the full git flow (branch, commit, push, PR). Confidence: 0.90
- When asked to put changes up as a GitHub PR, use the standard flow: create a descriptively-named branch (e.g., `fix/...`), stage only the relevant source files, commit with a conventional-commit message, push with `-u origin`, and open the PR with `gh pr create` (title matching the commit subject). Confidence: 0.70
- When the user asks to post something on GitHub (e.g., a follow-up comment on an issue), use the `gh` CLI to post it directly — the user expects the assistant to perform the action, not just produce text to copy-paste. Verify `gh auth status` first, then use `gh api` or `gh issue comment` as appropriate. Confidence: 0.80
- Before writing inline code for a task (especially PM-specific logic), first check if the project's shared utility libraries (e.g., `cli-helpers`) already have a function for it. Writing a bespoke inline solution when a helper exists wastes effort and frustrates the user. Named utility functions also make intent clearer than inline patterns (e.g., `importStatementPath` vs `.replace(/\\\\/g, '/')`). When the user asks "do we have a utility for this?", search for it instead of keeping the inline version. Confidence: 0.78
- When inline snapshot tests fail under npm/pnpm due to different dependency version resolutions, fix the root cause by aligning dependency versions across package managers — do not weaken/modify the test assertions to work around the discrepancy. Confidence: 0.75
- When testing across different package managers, always run `{pm} install` to generate the actual `node_modules` for each PM — do not skip install and reuse another PM's `node_modules`. Different package managers structure `node_modules` differently (hoisting, symlink layouts), and the test's purpose is to validate the project works with that PM's actual layout. Confidence: 0.70
- Do not discard taste/learning files when cleaning up unintended diffs — e.g., avoid `git checkout -- .commandcode/taste/...` to remove auto-learned noise. The user monitors these files and expects learned entries to persist; a revert wipes entries the user will notice and ask about. Revert only the intended code files, never the taste store. Confidence: 0.90
- When a codebase has parallel template variants for the same generated output (e.g., `sdl.ts.template` and `sdl.js.template` for TS and JS projects), apply changes to all variants and keep them in sync — patching only one leaves the other emitting stale output. Confidence: 0.75
- When asked to review or triage issues/tasks, rank by impact-to-effort ratio (high impact, low complexity first) and return a concise ranked shortlist (top N), not an exhaustive list. Include a one-line rationale per item and a single "do this one next" pick. Confidence: 0.75
- When the user asks for a simplification review of a PR (with bugs already reviewed elsewhere), focus solely on what can be simplified — flattening conditions, deleting indirection, renaming misnamed functions — rather than re-checking correctness or performance. Rank suggestions by impact, and flag what should NOT be simplified away. Confidence: 0.80
- The user uses Greptile (automated code review on PRs) and forwards its review comments for the assistant to triage and address. Treat a review comment as a claim to verify against the code, not as a directive to accept blindly. When a bot's claim is correct (e.g. "your test fixture exercises the wrong code path"), do the full rework to genuinely target the flagged branch — don't just shuffle the assertion. After the rework, verify the test still fails for the right reason when the production code is reverted. Confidence: 0.75
- When running an interactive CLI generator (e.g., `create-cedar-app`), always pass the skip-prompt flags (e.g., `--yes`) — invoking it without flags makes it hang waiting on interactive prompts with no input, which stalls the whole session for a long time. Confidence: 0.80
- When the user asks to commit changes, stage only the source files for the change (skip random untracked files / unrelated edits), use a conventional-commit style subject with scope (e.g., `fix(dbAuth): ...`), write a body that explains the _why_ (security impact, root cause) rather than the _what_, and pass the message via heredoc (`git commit -F -`) for multi-line bodies. Reference the originating issue/PR in the body. Leave working tree clean after. Confidence: 0.85
- When a code review surfaces an open gap (e.g., "worth a real smoke test" or a suspected regression/fragility), verify it empirically before asserting it as a finding — run the actual code path or read the existing files/conventions (e.g., check that sibling fixtures are also 0-byte before calling one "fragile"). Prefer running the check over answering from theory. Confidence: 0.80
- When a pre-push hook (or CI) fails on pre-existing, unrelated issues (e.g. type errors that exist on `main` before the current change, prettier issues in untouched files), do not let it block the push — use `git push --no-verify` to skip the hook and call out the skipped failures in the response so the user knows they're real, just out of scope. Don't burn the change trying to fix pre-existing mainline issues. Confidence: 0.75
- When force-pushing an amended or rebased commit to a branch that may have been pushed previously, use `git push --force-with-lease` (not bare `--force`) so the push is rejected if the remote has moved since the last fetch. Confidence: 0.85
- When handling review feedback on a PR, proactively push back on comments that are too nitpicky or that would expand the scope beyond the original PR goal — present the user with a categorized assessment (worth fixing / push back / already addressed / out of scope) and explain the rationale for each pushback rather than blindly implementing everything. Confidence: 0.80
